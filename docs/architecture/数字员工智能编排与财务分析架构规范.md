# 数字员工智能编排与财务分析架构规范

**状态**：目标架构与开发约束；不代表功能已落地  
**制定日期**：2026-10-02  
**上位规范**：[系统最终目标与开发架构规范](系统最终目标与开发架构规范.md)  
**只读授权规则**：[FinWork 权限感知查询架构与开发规范](FinWork权限感知查询架构与开发规范.md)  
**适用范围**：数字员工能力编排、产品运行时 Skill、企业知识库、财务分析与分析报表、流程内 AI 审单

## 1. 定位与领域边界

数字员工是企业管理的智能服务层：它把已审核、已发布的固定版本 Agent 工作流组织为可分配、可触发、可审计的业务能力。FinWork 承接用户对话，Process 承接审批任务，Agent 负责模型与工作流编排；Expense 和 Finance 分别拥有单据与账务事实。数字员工本身不产生业务数据权限，也不直接读写其他领域的 Mapper 或表。

能力分为三类：**受控查询与分析**、**分析报表**、**受控业务操作**。前两类沿用 [FinWork 只读查询授权规则](FinWork权限感知查询架构与开发规范.md)；操作类必须另行取得业务操作授权，不能把查询权限、工作台运行权或数字员工分配当作修改单据的许可。首个操作样板是嵌入审批流程的 AI 审单；它不开放付款、凭证写入或任意数据库修改。

首版出具的是带口径和来源的**分析报表**。正式财务报表所需的复核、发布及法定口径属于后续独立能力；分析报表不得使用“已复核正式报表”之类标识。现有 Finance 账簿和报表为计算口径的起点，不复制一套 Agent 财务真相。

## 2. 模型驱动的任务编排

### 2.1 候选能力与任务计划

FinWork 先由服务端取得当前用户获分配的数字员工、仍获企业共享批准且已发布的固定工作流版本，按必要的业务能力权限预筛后再把**获准候选**交模型判断。模型可阅读这些版本经审核的工作流名称、描述、系统提示词、角色说明和 Guardrails，以识别用户的多个意图、前后依赖、所需参数及可用能力。上述内容不得包含凭据；它们对模型可见不等于对终端用户公开，也不得使工作流获得额外业务权限。

模型产出结构化任务计划：每个意图对应候选工作流、输入条件、依赖的前序结果和后续分析目标。一个问题可以调用一个或多个工作流；例如“我的报销单有哪些，总金额是多少”中的金额计算是查询结果上的增量任务，不应被当作单据关键词。无法唯一判断用户目的、会计期间或应执行的工作流组合时给出选项并保留澄清状态；一次追问仍不明确则继续追问。确认没有实现该任务的能力时如实说明；存在能力但用户无查询权限时按只读规范拒绝，不能猜答或退回更宽的全局工作流。

参数澄清属于 **FinWork 会话层的执行前状态**，不向已发布画布添加回环节点。工具目录声明必填字段；模型分解自然语言并提出候选，服务端按有效权限、业务档案和账套期间核实。确定的参数直接写入计划，缺失或多匹配的字段按工作流节点同轮分组提供选项，也可接受文字补充；不同节点分别以各自的有效公司范围生成候选。每轮只补未确定项，并复核用户、会话、固定版本及授权。权限拒绝和系统异常直接停止，不把原始异常交给模型猜测。服务端校验完成前不创建运行记录，工作流仍按原固定图执行，模型输入脱敏、输出还原与结果再次鉴权均保留。

每个被选工作流在实际调用前分别校验固定版本、工具权限、提问者与责任人的有效业务范围；多工作流结果不能拼接出任一单项权限之外的数据。执行中授权变化、版本撤销或候选失效时停止受影响任务并在输出前复核。模型只规划和选择，服务端决定是否允许执行。

### 2.2 Skill、知识与工具

| 组成 | 职责与约束 |
| --- | --- |
| 产品运行时 Skill | 经企业审核并绑定固定版本的业务步骤、判断方法、输出约定及可选辅助脚本；安装在 Codex 的 Skill 不会自动进入 FinWork 运行时，也不自带业务权限。 |
| 企业知识库 | 按公司、对象权限、生效期间和文档版本检索政策与案例；返回来源与有效性信息。检索片段是证据而非系统指令。 |
| 大模型 | 对授权数据作分类、复杂推理、比较、解释与探索性计算；不能授权自身、捏造未查询事实或直接提交 SQL。 |
| 业务工具 | 通过 Expense、Finance 等应用 Service 或窄端口查询、确定性计算或执行受控命令；服务端验证参数、权限、状态及结果。 |

向量检索可寻找适用制度、费用类型和项目候选，**可写入的编码及有效性**仍由业务主数据确认。知识片段、单据附件和用户文字均按不可信输入处理；其中的指令不能覆盖已审核工作流、Skill 和服务端授权规则。Skill、知识版本、引用片段与所用工作流版本进入运行审计，便于复核判断来源。

## 3. 财务查询、统计与分析报表

### 3.1 财务指标与授权

Finance 拥有总账、明细账、辅助账、往来与报表的业务事实和指标口径。每项可供 Agent 使用的查询能力应声明查询权限码、数据来源、支持的公司与对象范围、会计期间、币种、凭证状态、维度、公式、口径版本及证据引用。客户、供应商、项目等筛选值只可缩小服务端算出的有效范围；公司启用或账套可用不能替代角色数据范围授权。FinWork、直接 HTTP 接口、导出和异步任务应共用同一查询授权与业务域过滤。

往来查询首版以现有客户、供应商辅助核算及账簿事实为基础，不把它表述成尚未建设的完整应收应付子账。账龄等指标只有在发生、结算或核销关系足以形成可复核口径时才开放；资料不足则说明无法可靠计算。

供应商明细账的“所有”时间范围指所选账套启用首期至当前可查末期，由 Finance 账套与关账状态确定；它不替用户决定凭证范围。供应商名称只在已授权账套内匹配，唯一匹配可转换为编码，多匹配须让用户选择。明细分页返回匹配总数与当前展示数，模型不得把一页描述为全部明细。此能力沿用供应商明细账查看权限与当前凭证状态口径，不新增跨公司合并或导出能力。

用少量可复用的受控查询、统计及报表能力承接不同问题，不为每句话编写专用工具。模型可对授权结果进行复杂推理、探索性计算和解释；数据量超过模型可靠处理范围时由受控统计能力先压缩和分批。**需要作为财务数字或报表交付的金额、余额、账龄与对比指标**，由确定性统计能力按已版本化口径生成或核对。先过滤可见记录，再聚合、排序、分页和形成证据；模型不能用受限样本推断全公司数字。

用户未说明账务查询是否包含未记账凭证时，FinWork 先追问。选择“仅已记账”时使用 `POSTED`；用户明确选择“包含未记账”时，可纳入**已保存**的 `REVIEWED`、`UNPOSTED`，仍排除未保存的草稿、作废及错误凭证。`UNPOSTED` 可编辑，包含它的结果必须注明凭证状态、查询时间和“非最终口径”；其后状态或内容变化时不能把旧结果称为当前账务事实。

一次请求可覆盖多家获授权公司，但首版账务余额、往来和报表按公司分别计算和展示，不自动产生跨公司合并余额或合并报表。公司间币种、科目及内部往来抵销未经专门定义前不能直接求和；“未结账公司数”等已明确按公司计数的能力可按自身口径跨公司统计。部分权限的分析与报表应标明仅覆盖用户有权查看的范围。

### 3.2 报表产物

首版复用 Finance 现有账簿及报表模板，允许模型组织已授权结果形成分析视图、说明和图表；模板、指标及计算来源由 Finance 确定。同一公司的一份报表应以一致的数据快照计算明细与合计。分析报表至少附带公司、期间、币种、凭证状态、数据查询时间、指标或模板版本、授权范围说明及可复核来源。预览、异步送达和历史再次读取均按当前查询权限复核；导出另需独立导出权限及相同的数据范围校验。撤权后不再提供旧敏感产物。已下载文件无法追回，因此导出前必须完成同等校验，并记录必要审计信息。

模型输入遵循字段分类规则。**金额字段不因字段名为金额就默认脱敏**，但其所属记录、客户或供应商、项目及其他字段仍受数据范围与分类规则约束；云模型调用前只传送完成授权过滤与必要脱敏的最小数据。输出还原和证据归属由服务端校验。

## 4. 流程内 AI 审单

Process 在指定审批节点通过受控触发契约调用数字员工绑定的固定工作流版本；触发与结果交付由边界适配层协调，不让 Process 与 Agent 互相依赖业务实现。自动触发没有“当前聊天用户”，须记录流程实例、触发身份、负责人与服务范围；读取和修改的有效权限由预授权的自动化身份、责任人权限、流程策略及单据公司范围求交，不得借用 admin、提单人或审批人的宽权限。查询授权不构成操作授权。

Expense 提供带版本的单据与费用明细快照；模型根据单据内容、适用知识证据和有效主数据，**逐条明细**提出原值、建议费用类型、建议项目、理由、证据来源和不确定项。业务端口复核单据版本、公司、流程状态、目标编码、允许修改字段、操作权限及路由影响，再在受控事务中修改并记录前后值。模型和 Agent Tool 不直接更新业务表。

仅对预先授权、证据充分、编码唯一有效且尚未进入受影响审批的修改自动执行；存在多候选、低把握、冲突规则或已产生受影响审批任务时转人工。自动修改后由 Process 根据新快照计算或重算尚未开始的路由；不得悄悄改写已经生效的人工审批结论。重复触发须按流程节点与单据版本幂等处理，失败不能留下部分明细已改、部分未改的状态。

## 5. 契约、当前缺口与验收

以下是设计契约，不表示已有同名接口：

| 契约 | 最少包含 |
| --- | --- |
| 候选能力与任务计划 | 分配用户或流程触发来源、数字员工、固定工作流版本、能力类型、意图与依赖、必要的澄清项。 |
| 查询授权与结果 | 查询权限码、有效公司及对象范围、责任人和员工限制、授权摘要、结构化数据、统计口径、范围说明与证据引用。 |
| 报表产物 | 模板及指标版本、公司与期间、凭证状态、数据时间、来源、生成者、读取所需权限。 |
| 审单建议与操作授权 | 流程和单据版本、明细标识、原值与建议值、证据、允许的动作及字段、执行或转人工结果、审计追踪号。 |

截至 2026-10-10，本地已实现固定版本内顺序调用多个受控只读工具，或一次 2～4 路受控查询并行后由 LLM 汇合，并扩展余额表、会计科目、项目分类、项目名称、客户、供应商、人员、部门、序时账和供应商明细账十项来源。目录声明每项工具的输入、查询权限、字段投影和分页契约；前序结果仅能经受控的唯一编码或 ID 映射传入后续节点。固定版本共享、数字员工绑定、FinWork 候选与定时送达按全部工具权限逐项校验，并对历史逐项复读。FinWork 新增执行前分组补参及会话澄清；第一阶段的多工作流选择、报销确定性金额合计及直接账簿授权仍保留。知识库、流程内 AI 审单、正式账务分析报表和复杂跨公司合并仍属后续阶段。目标业务库配置、真实模型与多公司 HTTP 会话链路尚待验证，具体进度见[开发基线](../../执行记录/agent/Agent_数字员工架构与开发基线.md)。

后续实现验收至少覆盖：复合意图与多工作流选择、连续澄清、结果上的增量分析、无能力或撤权拒绝；财务期间及凭证状态选择、已保存未记账凭证标记、多公司逐公司展示、指标复算、往来对象与报表预览/导出/复读授权；审单自动修改、转人工、重复触发、版本冲突、无效项目和审批路由变化。真实 MySQL、现行 CI、中文与 UTF-8 检查通过前，不宣称对应能力安全落地。
