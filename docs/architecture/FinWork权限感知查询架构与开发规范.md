## 1. 目标、边界与当前事实

用户通过 FinWork 提问时，系统只能调动该用户获分配的数字员工所绑定的、已发布且已授权的 Agent 工作流。查询前确定当前用户的功能权限和数据范围，查询时在业务域内过滤，输出前再次审核。统计、明细、证据引用、聊天历史、工作台运行记录和异步结果都属于受保护的输出。

本规范覆盖**只读业务查询、统计及分析报表的数据授权**。审批、付款、凭证写入和其他命令须使用独立的业务操作授权、状态校验及适用的人工确认或预授权自动执行规则，不能因为接入 FinWork 而继承查询许可。流程内 AI 审单的操作规则见[智能编排专项规范](数字员工智能编排与财务分析架构规范.md)。Agent Tool 不直接访问 Expense、Finance、Process 的 Mapper 或业务 Entity；继续采用单部署模块化单体及现有应用 Service/窄端口。

截至 2026-10-10，本地已扩展十项受控只读工具，并为固定版本增加单链路或一次受控并行区执行；第一阶段的模型任务计划、多工作流执行、报销完整授权集合金额合计和直接读取范围校验继续保留。FinWork 的分组补参和供应商明细账代码也已加入；目标业务库配置和真实模型会话仍须按[数字员工开发基线](../../执行记录/agent/Agent_数字员工架构与开发基线.md)核验。本地实现不等于功能已获准上线。

## 2. 权限模型与唯一授权来源

### 2.1 查询能力与角色范围

每个业务查询模板必须声明唯一的**查询权限码**、数据所有者、支持的范围类型和结果字段。查询权限码是系统设置角色权限体系中的正式权限，不以 `agent:chat:view`、`agent:chat:send`、工作台运行权或菜单可见性替代业务查询权。原有菜单和按钮权限保留；新查询能力可复用语义完全一致的业务只读权限，语义不一致时增加专用查询权限码。工具、模板、工作流发布时校验声明，运行时再校验一次。

一条角色数据范围配置以 `(role_id, query_permission_code)` 唯一定位。该角色必须同时持有有效查询权限码和有效范围配置，才构成一次授权；角色停用、权限撤销或范围配置删除后立即失效。**不得**把角色 A 的查询权限与角色 B 的数据范围拼接成更大权限。普通角色未配置范围时，对该查询默认拒绝。

首版范围类型：

| 范围 | 服务端解释 | 适用限制 |
| --- | --- | --- |
| `SELF` 本人 | 报销查询仅匹配当前提问者提交或分配给其处理的单据，可跨付款公司；具体关系由查询能力声明 | 只扩展个人关系，不授予查看同公司其他人的单据；责任人和数字员工服务范围仍须允许该付款公司 |
| `DEPARTMENT_TREE` 本人所属部门及下级 | 从服务端当前有效员工部门关系和部门树求提交人集合；该集合的单据可跨付款公司 | 不沿跨公司组织关系扩展人员集合；无有效部门则范围为空；责任人和数字员工服务范围仍须允许该付款公司 |
| `SELECTED_COMPANIES` 指定公司 | 角色配置的有效公司编码集合 | 至少选一家；服务端确认公司存在且可授权 |
| `ALL_COMPANIES` 全部公司 | 当前租户内所有有效公司 | 仅超级管理员可授予；普通角色不能自授或代授 |

每项查询能力仅开放有明确业务语义的范围。公司结账统计首版只接受 `SELECTED_COMPANIES`、`ALL_COMPANIES`；不能把 `SELF` 或部门范围默默解释为用户所属公司。对于报销查询，`SELF` 须分别声明“我提交的”或“分配给我的”，不得由模型自由扩大为“我能看到的所有单据”。

同一用户持有多个有效角色时，仅在**同一查询权限码内部**并集其有效范围；然后与后述数字员工等限制取交集。报销查询的 `SELF` 和 `DEPARTMENT_TREE` 是经明确配置的跨付款公司对象关系范围，不能泛化到其他查询能力或直接替代责任人与员工的公司限制。租户边界、软删除和对象可见性始终是独立的强制约束。超级管理员指系统保留角色 `super_admin`，其查询范围固定为当前租户全部公司；仍需经过认证、业务查询能力白名单、工作流绑定、审计和输出校验，不拥有跨租户豁免。

### 2.2 可审计的有效授权

运行时由服务端依据已验证的用户身份、有效角色和权限、数据范围配置、组织和公司主数据计算 `QueryAuthorization`。它至少表达：提问者、责任人、查询权限码、业务范围、有效公司/部门/个人约束、工作流与工具版本、计算时间和授权版本或摘要。`companyId`、部门、角色、范围与超级管理员身份均不得信任聊天输入、工作流画布变量、前端选择或过期 JWT 权限快照。

缺少身份、角色、范围、有效组织关系或必要的授权元数据时，敏感查询失败关闭。客户端只可提交业务筛选条件，例如日期、单据状态、关键词和上限；这些条件与授权范围相交，不能覆盖授权范围。权限配置变动后，新请求和异步执行开始前重新读取有效授权；发布状态或责任人权限变化同样如此。缓存若将来引入，必须有可验证的失效机制，不得作为当前实现的前提。

## 3. 系统设置：数据可见范围

在“系统设置 → 权限管理 → 选择角色”后，上方将“菜单与按钮权限”和新增“数据可见范围”并排显示；“用户角色分配”仍在下方。数据范围面板只列出该角色**已保存授予**、并被查询能力目录标记为数据查询的权限。每行显示查询名称、权限码、业务说明、允许范围选项；选择 `SELECTED_COMPANIES` 时显示公司多选。未选角色显示选择提示；尚未保存的权限树更改不能提前激活范围配置，界面提示先保存菜单与按钮权限。

前端隐藏和禁用仅用于交互，后端独立鉴权。读取角色范围使用角色查看权限；写入采用独立的 `settings:roles:assign_data_scope`，与现有 `settings:roles:assign_permissions` 分开。超级管理员角色范围固定为全部公司，在面板中只读显示。其他角色的授权者只能授予自己对**同一查询权限码**拥有的范围；只有超级管理员可以设置 `ALL_COMPANIES`。对于随被授权人而变化的 `SELF` 和 `DEPARTMENT_TREE`，不能只比较管理员当前的部门：保存范围、分配角色和变更组织关系时都须检查受影响用户的实际可见集合不会超出授权者的可委派范围；无法可靠证明时只允许超级管理员操作。后端验证角色状态、查询权限是否已授予、范围是否被该能力支持、公司是否有效、授权者是否越权；一次保存要么全部成功，要么不改变原配置。每次变更记录操作者、角色、权限码、变更前后范围和时间。

接口契约建议沿用现有 `/auth/system-settings/roles`：

```text
GET /auth/system-settings/roles/{roleId}/data-scopes
PUT /auth/system-settings/roles/{roleId}/data-scopes

请求体：{ scopes: [{ permissionCode, scopeType, companyIds }] }
响应体：该角色当前有效的数据范围配置和各查询能力允许的范围类型
```

`PUT` 是该角色数据范围的整体替换，与菜单权限保存事务相互独立。`SELECTED_COMPANIES` 的 `companyIds` 为非空、去重的业务字符串编码；其他范围不得携带 `companyIds`。重复权限码、未知权限码、未授予权限码、非法范围、无效公司或越权授予均整体拒绝，不静默忽略。保存菜单权限后，失去查询权限码的旧范围配置必须同步删除或立即变为不可用；再次授予该权限时不自动恢复旧范围。

持久化采用角色与查询权限码唯一的范围主记录，并用关联记录保存指定公司编码，避免以自由 JSON 充当授权规则。迁移只创建表、权限码和必要索引，不向普通角色自动赋予宽范围；现有普通角色的 Agent 数据查询在配置前默认拒绝。超级管理员的全部公司范围由系统保留角色规则确定，不能依赖手工插入的某条配置。数据库迁移须幂等、可回滚，发布前对角色、权限和公司引用进行校验。

## 4. FinWork、数字员工与工作流

### 4.1 选择和执行顺序

```text
已认证提问者
  → 查询该用户有效的数字员工分配
  → 限定经企业审核、已发布且通过必要权限预筛的绑定工作流固定版本
  → 模型依据获准能力信息识别复合意图并选择一个或多个工作流；不确定则持续澄清
  → 对每个候选分别检查提问者、责任人、员工配置、工作流与工具权限
  → 业务域只读端口按各自有效授权过滤、查询；Finance 按指标口径计算
  → 字段分类与必要脱敏后，模型对最小结果完成增量分析
  → 对模型给出的财务数字做确定性核对；结果组装与证据核验，输出前复核
  → 保存受控回答及最小审计记录
```

绑定必须记录提问用户、数字员工、责任用户、工作流 ID、固定版本、状态及员工配置范围。一个用户可被分配多个数字员工。模型可阅读**获授权候选版本**经审核的工作流名称、描述、系统提示词、角色说明及 Guardrails，以理解能力边界；其中不得含凭据，也不得将这些内容直接公开给终端用户。多个意图可选择多个工作流；目标、参数或是否需要同时执行仍不确定时给出选项并继续澄清，不能任取第一个。简单或复杂的增量分析均可由模型承担，但模型不能借此扩大查询范围或编造事实。数字员工自身不产生业务权限。每个工作流的实际可访问集合分别为：

```text
提问者对该查询权限码的数据范围
∩ 责任人对同一查询权限码的数据范围
∩ 数字员工配置范围
∩ 工作流发布状态与绑定版本
∩ 工具/模板允许的权限与范围
∩ 当前业务对象及请求筛选条件
```

任一必需条件不满足即拒绝。多个工作流的结果不能拼接成任何单项权限之外的数据。不存在绑定或已发布工作流时，不得进入未授权的内置回退，也不得把业务查询转为普通聊天请求交给模型猜答；确认没有实现该任务的能力时如实说明，存在能力但缺少查询权限时按第 4.3 节固定拒绝。工作台手动测试和异步运行经过同一授权入口；测试者只有工作台运行权限但没有业务查询权时仍不能读取业务数据。异步任务显式传递身份标识和追踪号，在开始执行及交付结果前重新计算授权，不继承线程中的旧权限快照。能力发现、任务计划和连续澄清的详细契约见[智能编排专项规范](数字员工智能编排与财务分析架构规范.md)。

### 4.2 查询端口与结果

报销单的 `pm_document_instance.company_id` 是服务端维护的**单据公司归属快照**：表单设计或已保存快照中存在有效的付款公司时取付款公司 ID，否则取本次保存时提单人所属公司 ID。单据类型不能决定是否有付款公司；申请单也可能配置该组件。创建、草稿保存和驳回重提须在保存表单的同一事务内同步快照，正式提交后冻结；付款公司无效或多值时拒绝，不得回退到提单人公司。Agent 统计和凭证归属以该快照为准；审批路由的付款公司条件及实际付款账户匹配仍按各自业务字段校验，不能用回退值伪造付款公司。

历史单据只依据其保存的表单设计与表单数据回填付款公司；没有付款公司的旧单据须取得创建时提单人公司的可靠凭据及人工确认映射，不能从当前用户档案猜测。未确认归属的记录保持不可用于受控查询，全部核实后才可收紧 `company_id` 非空约束。迁移前备份、迁移后核对零空值及重复执行；历史聊天和测试运行是生成时快照，不因回填自动改写。

Agent 域负责入口、选择、编排和审计；授权解析由 System/Auth 负责；Expense、Finance 等数据所有者负责将授权条件落实到数据库查询。新增 Tool 只调用对应业务域受控只读端口，使用参数化查询和明确字段的读模型，禁止自由 SQL、跨域 Mapper 直连或把工作流变量当作授权表达式。

先筛选可见记录，再做 `COUNT`、求和、分组、分页与摘要；分页总数和证据标识也不得来自更宽的查询。查询端口应返回结构化结果、范围说明和可授权核验的证据引用。结账样板以明确的会计年度和期间为输入：若用户只说“当前”，先从可信财务上下文确定唯一期间；跨公司期间不一致或上下文缺失时请用户澄清，不混算不同期间。Finance 端口在有效公司集合内统计未结账公司：有权限且没有未结账公司是 `0`，没有可访问公司或查询权限则是拒绝。

账务统计、往来查询和分析报表也必须逐项声明查询权限码与有效范围；客户、供应商、项目和公司等筛选条件只会收窄授权。Finance 维护指标的来源、期间、币种、凭证状态、公式、维度、版本及证据。复用受控查询与统计能力，不能让模型执行自由 SQL。需要作为财务数字或报表交付的金额、余额、账龄和对比指标由确定性能力按已授权数据生成或核对；模型可对授权结果进一步推理和解释。

**受控工具目录扩展：** 余额表与序时账分别沿用各自账簿查看权限码；会计科目、项目分类、项目名称、客户、供应商和部门档案各有独立查询权限码；人员查询使用单独授予的当前租户全企业查询权限。供应商明细账复用 `finance:general_ledger:supplier_detail_ledger:view` 的逐项角色范围，并由 Finance 在授权账套内解析供应商编码和生成账簿结果。账套参数在服务端与工具权限对应的数据范围相交，档案“全量”指授权账套内可分页遍历的全部记录，只返回固定字段投影。人员按姓名包含匹配，只输出 `id`、`username`、`position`、`labor_relation_belong`。序时账只输出约定的 `gl_accvouch` 字段；余额表和供应商明细账复用 Finance 现有账簿口径。账务工具必须明确会计期间及凭证范围，包含已保存未记账凭证时说明查询时间与非最终口径。分页总数与当前页不得混称为完整明细。

FinWork 在创建受控运行前，依据工具目录逐字段补参。模型提出的账套、供应商和期间只作候选；服务端以提问者、责任人和数字员工服务范围的交集校验名称与编码。多个缺项在同一轮按工作流节点及字段分组提问，不把不同工具的公司范围合成一个全局交集；选项与会话、用户、固定版本和授权摘要绑定，后续每轮重新鉴权。用户说“所有”且未给日期时，期间解释为该账套启用首期至当前可查末期；这不构成“包含未记账”的选择，凭证范围仍须明确。无法确定的参数不得生成失败运行，撤权或版本变化后的旧选项不得继续执行。供应商明细账只表示现有辅助核算账簿，不延伸为应付、付款或核销子账；查询结果标示匹配总数、展示条数、实际期间、凭证口径及查询时间。

固定版本可为原有单链路，或“开始 → 可选顺序查询 → 2～4 个并行受控查询 → 一个末端 LLM → 结束”。首版只有一个并行区，每条分支恰好一个查询节点，全部分支完成后由 LLM 汇合；工作流总工具数不超过 9。兄弟分支不能相互引用，只能引用并行区之前已完成的顺序结果；循环、嵌套分支、悬空节点和汇合后继续查询均不得保存或发布。共享审核记录全部工具权限码；数字员工按每项权限配置只会收窄的公司上限。执行前、每个查询分支前、模型接收结果前和输出前逐项复核；前序映射只允许唯一记录中声明的编码或 ID 字段，并复核来源账套与目标账套。任何分支失败、超时或撤权时整条结果失败，不向模型或用户交付部分数据。汇合结果按画布节点顺序保留各自的来源、范围、数量及分页状态；不同查询的金额和记录数不自动相加，只有全部来源为空才标记零结果。聊天和定时结果按工具保存来源，复读时逐项复核；任何来源缺失、撤权或来源数据无法核验时拒绝整条结果。历史单工具计划沿用原契约。新增迁移 `backend/sql/migrate_agent_controlled_tools_20261009.sql` 须在启用新工具前由目标环境执行并核验，不自动给普通角色授予宽范围。

### 4.3 输出、历史与模型边界

模型不能决定授权、补充未查询的事实或凭自然语言声称扩大范围。先按字段分类并做必要脱敏，再把已授权的最小结果送到模型；金额字段不因字段名为金额就默认脱敏，其所属记录和其他字段仍受范围与分类规则约束。模型可完成复杂分析及探索性计算；需交付的财务口径数字、明细证据和范围说明以业务域已授权的结构化结果确定或核对。输出前重新确认授权与证据归属；自由文本无法可靠核验时，使用本地确定性模板生成回答，不能仅凭提示词或正则扫描宣称安全。

完全没有相关查询权限或有效范围时，回答固定为：**“系统查询到您没有相关权限，请换一个问题”**。有权限但匹配结果为空时回答零，并可说明期间。只拥有部分范围时必须写明**“仅统计您有权查看的范围”**；不能用受限数据推断全局总量，也不能透露被拒绝的公司数或名称。

读取聊天历史、工作台运行记录、步骤详情、导出及异步结果时再次按当前权限审核。受控回答须关联查询权限码、工作流版本、数据对象或证据来源及授权摘要，使重新读取时能验证来源；没有可靠来源信息的旧敏感记录按不可验证处理。撤权后阻止再次读取历史敏感结果；已向用户交付或导出的内容无法事后收回，因此运行步骤和日志默认只保留必要的权限摘要、数量和追踪信息，禁止长期保存未脱敏原始记录。既有普通聊天的模型路径不得承接识别到的数据查询；历史消息送模型前需防止把旧查询结果重新带入无权限会话。模型故障、脱敏失败、授权变化或证据不匹配时拒绝业务数据输出并保留可排查的非敏感错误记录。

Agent 工作台的**手动测试运行**属于受限调试例外：测试入口须由服务端固定来源标记；读取详细步骤日志和该次测试输出，必须同时具备工作台日志查看权限和运行记录归属。`agent:workbench:view_logs` 是查看本人既有测试日志的独立调试授权，撤销后立即不可再读；新测试查询仍按测试者当前的业务查询权限与数据范围执行。FinWork、定时运行和其他来源不得借用工作台来源标记开放日志；普通聊天用户不会因此获得工作台日志权限。调试记录不得额外保存未经业务授权过滤的原始查询记录。

### 4.4 账务口径与分析报表

账务、往来和报表能力分别声明查询权限码、适用范围和结果字段；用户选择的公司、往来对象、项目、期间及凭证状态只能缩小授权。多公司数据先按每家公司有效范围查询，再形成各自的明细与统计，不以模型汇总替代尚未定义的跨公司合并口径。

分析报表的预览、导出、异步送达及历史读取须按当前权限和证据来源复核；导出还需独立的导出权限，不能以查询权限代替。权限撤销后不得再次交付旧敏感产物。凭证状态选择、分析报表口径与产物信息由[智能编排专项规范](数字员工智能编排与财务分析架构规范.md)统一规定。

## 5. 推进顺序、验收与发布门禁

1. 先完成查询能力目录、角色数据范围保存/读取及权限配置审计；普通角色默认拒绝，验证超级管理员和委派管理员的授权边界。
2. 再实现统一授权解析、数字员工用户绑定、固定工作流版本及 FinWork/工作台/异步共用入口；封闭旧工具路径和未授权回退。
3. 逐个业务域迁移只读端口。先用报销查询回归本人、待办和部门范围，再增加财务“指定期间未结账公司数”样板，随后接入账务、往来和分析报表。同一数据若仍可经直接 HTTP 查询接口绕过新授权，必须先统一授权或关闭该入口，否则不得发布对应的权限感知查询能力。
4. 最后验证回答、历史、运行日志、异步结果与撤权后的再次读取；上线前完成真实 MySQL、多公司和真实模型路径冒烟。每一切片保留现有 API 兼容或提供独立迁移/回滚方案。

第一阶段已在报销列表、审批待办、付款单、个人未结事项及单据查询处增加逐项角色范围过滤；详情、打印及关联附件增加对象复核，通用附件预览校验上传者或当前可读的关联单据。异步导出在提交、执行和下载时重新校验范围及来源；缺少可信来源的旧敏感导出不交付。目标环境仍须回归历史附件、导出及角色切换行为，尤其不能仅凭公司快照回填推断直接入口已安全。

第一阶段已将账簿元数据、九类查询和 Excel 导出绑定到对应查看权限的数据范围；导出继续要求独立导出权限。指定公司须在该查询能力的范围内，元数据在多家公司获授权时要求明确选择。期间状态接口维持同一公司范围校验。财务分析报表和往来能力仍属于后续阶段。

最低验收矩阵：无权限、仅菜单权限、查询权限无范围、本人、本人多部门及下级、指定一/多公司、全部公司、多个角色同码并集与跨码不混用、停用用户/角色/员工、责任人范围更窄、工作流撤销或改版、公司与部门删除、租户隔离、无数据返回零、部分范围标识、跨公司期间歧义、模型捏造证据、授权中途撤销、聊天历史与日志复读、异步重试和线程上下文清理。所有失败路径均不得把原始查询记录写进可读日志。后端定向测试、前端组件与交互测试、现行 CI 质量门禁和相关数据库迁移验收通过后，才可宣称本规范落地。

账务与编排扩展还须验证：复合意图、多个工作流及连续澄清；“单据列表＋总金额”不误将金额问题作为关键词；未说明凭证状态时追问，明确选择后排除未保存草稿；`UNPOSTED` 结果标注；多公司逐公司展示；往来对象权限、指标复算、分析报表预览/导出/历史复读及撤权。AI 审单的操作授权与转人工验收由[智能编排专项规范](数字员工智能编排与财务分析架构规范.md)约束，不用只读查询验收代替。
