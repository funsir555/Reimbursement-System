## 2. 扫描范围与方法

### 2.1 扫描范围

本轮扫描覆盖以下三条线：

- backend：`backend/auth-service/src/main/java`
- frontend：`frontend/admin-web/src/views` 及 `src` 下主要页面 / helper / editor
- 文档配置与运行链：根目录、`docs/architecture`、`执行记录`、启动脚本

明确排除：

- `.git`
- `node_modules`
- `target`
- `dist`
- `storage`
- 其他可再生产物

### 2.2 扫描方法

本轮使用 PowerShell 本地只读扫描，以文件行数为基础指标，并叠加以下人工判断维度：

1. live truth 集中度
2. 跨域耦合度
3. 用户操作面 / 运行面暴露程度
4. 现有 owner / facade 是否已经收口
5. 是否属于新一轮二次膨胀基座

说明：

- 行数不是唯一真相，但在本仓库当前阶段，超大 View、AbstractSupport、DomainSupport 仍然和治理风险高度正相关。
- 本轮排序是“代码治理优先级”排序，不等于“谁最大就一定先动”；已完成收口的类不会因为行数还在就重新挤回主位。

## 5. 本轮选题建议

### 5.1 下一主批次建议

建议下一主批次切到：

> `frontend/admin-web/src/views/settings/SystemSettingsView.vue`

理由：

- 它是当前全项目单文件体量第一的 live 页面热点
- 它直接承载系统设置真相，而不是纯展示型页面
- 它跨多个配置子域，继续堆功能最容易形成前端层的第二轮 mega page
- 它和 `AbstractSystemSettingsDomainSupport.java` 构成天然的前后端联动治理对象
- 在 second-wave 四个后端热点全部收口之后，继续只盯后端会错过当前真正最活跃的 live truth 风险面

建议终态：

- `SystemSettingsView.vue` 压成 orchestrator view
- 真正的 live truth 下沉到 `panel / section / composable / schema / api-module`
- 保留现有路由、页面入口、权限口径和主要 API 协议不变

### 5.2 陪跑 / 预研位建议

本轮建议只设一个轻量陪跑 / 预研位，不开第二个重治理批次：

> `backend/auth-service/src/main/java/com/finex/auth/service/impl/expense/AbstractExpenseDocumentSupport.java`

定位：

- 当前不直接并发做完整重构
- 先做 owner map、流入冻结、职责切片和依赖白名单设计
- 等 `SystemSettingsView.vue` 主批次收口后，再决定是否把它提升为下一批 backend 主对象

### 5.3 暂不进入主位的对象

以下对象保留在高优先观察位，但本轮不建议抢占下一主批次：

- `frontend/admin-web/src/views/process/ProcessFlowDesignerView.vue`
- `frontend/admin-web/src/views/expense/components/ExpenseRuntimeFormEditor.vue`
- `frontend/admin-web/src/views/expense/ExpenseDocumentDetailView.vue`
- `backend/auth-service/src/main/java/com/finex/auth/service/impl/process/AbstractProcessManagementSupport.java`
- `backend/auth-service/src/main/java/com/finex/auth/service/impl/expense/AbstractExpenseWorkflowSupport.java`
- `backend/auth-service/src/main/java/com/finex/auth/service/impl/fixedasset/AbstractFixedAssetSupport.java`

原因不是它们不重要，而是为了遵守长期工作流的原则：

- 每轮只选 `1` 个主热点
- 陪跑位最多 `0-1` 个
- 避免刚完成 second-wave 后，又因为并发过多重新失控

## 6. 与旧顺位的关系

本轮需要明确清理以下旧口径：

- 不再沿用 `ProcessFlowDesignServiceImpl -> ExpensePaymentDomainSupport -> ExpenseRelationWriteOffService -> ExpenseSummaryAssembler` 作为下一批顺位
- 上述四个对象已完成 second-wave 正式验收，现阶段转入 completed / frozen facade 基线，不再继续挂在“下一步”位置
- 新一轮优先级已经切换为“前端 L1 大页面优先 + backend L2 mega base 预研跟进”的组合

## 7. 下一步实施入口

如果按本次 re-rank 直接开新批次，建议入口固定为：

1. 先为 `SystemSettingsView.vue` 做边界建模，明确 panel、section、schema、api、store 的分层
2. 同步标记 `AbstractSystemSettingsDomainSupport.java` 的 allowed owner 和禁止继续吸入的新职责
3. 只做一轮 focused tests / 页面交互护栏补齐，不和其它大页面并发开刀
4. 主批次验收后，再决定下一批是在 frontend 继续推进 `ProcessFlowDesignerView.vue`，还是切回 backend 的 `AbstractExpenseDocumentSupport.java`

## 8. 结论

- 本轮 re-rank 的最大变化，不是“又换了一个后端大类”，而是确认当前全项目头号风险已经从 second-wave backend coordinator，切换成 frontend mega view 与 backend mega base 的双峰结构。
- 因此下一轮治理不应机械延续旧的 Java 类名队列，而应按新事实切到 `SystemSettingsView.vue` 主批次，并把 `AbstractExpenseDocumentSupport.java` 作为 backend 预研位。
- 当前基线保持：backend `556/556`，frontend `211/211`，文档状态继续按 2026-04-24 的统一口径执行。
