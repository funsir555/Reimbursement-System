更新时间：2026-04-25

## 1. 治理目标

- 先止住“继续长屎山”的趋势，再持续把高风险热点压成稳定边界
- 不激进重命名，不直接走微服务拆分，不一次性推翻现有可运行结构
- 每一批都必须可独立验收、可独立回滚、可独立复盘
- 文档、配置说明、启动链与代码治理必须同步推进

## 3. 总体治理原则

1. 先止血，再瘦身，再收口
2. 所有治理按“先抽边界、再迁移调用、最后收口旧入口”的三段式推进
3. 新功能禁止继续堆进旧热点文件
4. 对外契约默认保持稳定：不改 URL、不改核心接口签名、不改前端 `@/api` 导入方式
5. 每一批都必须完成 compile、focused tests、full test、文档同步四层验收

## 5. 风险控制与备份策略

- 涉及热点大文件、跨模块迁移、配置入口、启动脚本或公共契约调整时，先备份再实施
- 备份目录固定放桌面，使用时间戳命名，例如 `C:\Users\funsir\Desktop\报销系统-backup-YYYY-MM-DD-HHMMSS`
- 推荐命令：

```powershell
robocopy "C:\Users\funsir\Desktop\报销系统" "C:\Users\funsir\Desktop\报销系统-backup-YYYY-MM-DD-HHMMSS" /E /COPY:DAT /R:1 /W:1 /XJ
```

- 返回码 `0-7` 视为成功，`8+` 视为失败；失败则停止进入实施阶段
- 备份验证至少检查：目标目录存在，且顶层包含 `.git`、`backend`、`frontend`、`docs`

## 6. 批次实施与验收规则

每一批固定按以下顺序执行：

1. 抽边界
2. 迁移调用
3. 收口旧入口
4. 定向测试
5. façade / 契约回归
6. 全量回归
7. 文档回写

明确禁止：

- 带着编译红灯进入下一批
- 带着主链路断裂进入下一批
- 以“后面再补”为理由继续往热点文件堆新逻辑
- 在文档仍写旧状态时宣告批次完成

## 7. 对外契约与内部演进约束

### 7.1 默认不动的对外契约

- controller URL
- 既有 service 接口签名
- 前端 `@/api` 导入路径
- 核心 DTO / VO 字段名
- money 字段表达方式

### 7.2 允许的内部演进方式

- 新增 domain service / support / assembler / module file
- 旧入口先兼容委派，再逐批收口
- 新增 owner 必须边界清晰，禁止桥接层搬家后继续长成新大基座

### 7.3 禁止的内部演进方式

- 激进重命名
- 未稳定前先拆微服务
- 直接推翻现有 working facade / barrel / route 结构重写
