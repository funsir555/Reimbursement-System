### 2.1 口径

本报告区分以下五种核验状态：

- **确认存在**：代码、配置或测试结果可直接证明。
- **部分存在但原因错误**：现象存在，但旧报告把不同概念混为一谈，或给出了错误归因。
- **证据不足**：只能看到数量或命名，不能证明重复、缺陷或性能问题。
- **不建议治理**：当前实现合理，治理收益不足以覆盖功能风险。
- **条件触发后治理**：只有满足明确部署、性能或可靠性条件后才实施。

## 三、逐项核验与治理决策

### 3.1 上下文管理

**核验状态：部分存在但原因错误。**

旧报告把 `ExpensePaymentSupportContext`、`PostVoucherRunContext`、`VoucherContextSupport` 等类与 ThreadLocal 上下文并列。这些类多数只是一次业务调用中的参数、依赖或运行数据载体，并不持有线程局部状态，不能据此得出“三套 ThreadLocal 管理”的结论。

实际存在的线程上下文主要是：

- `SecurityUtils.CURRENT_USER_ID`
- `TenantContext.CONTEXT`
- `TraceContext.TRACE_ID`

`AgentExecutionContext` 是可序列化快照对象，但当前没有生产调用方，属于未完成或暂未接入的抽象，而不是第三套正在运行的 ThreadLocal。

真正风险：

1. `AgentWebConfig` 将租户拦截器注册到 `/api/agent/**`，实际控制器使用 `/auth/agent/**` 和 `/auth/agent/workbench`，上下文拦截器无法覆盖目标接口。
2. `SecurityUtils.getCurrentUser()` 只构造带 ID 的临时 `User`，不会加载 `companyId`；`TenantContextInterceptor` 因而可能回退到公司 `1`。
3. 系统目标是单租户私有部署，但业务上支持多个公司。`tenantId=default` 可以是部署级常量，不能代替真实公司隔离。
4. `AuthInterceptor`、request attribute 和 Agent ThreadLocal 并存，身份来源和生命周期缺少一个清晰契约。

**治理决策：**

- P0 修复 Agent 拦截路径，禁止吞掉上下文构建异常后继续执行敏感请求。
- 在 Web 边界根据已验证 token 和数据库用户记录构建真实身份，至少包含 `userId`、`username`、`companyId`。
- 业务 Service 继续显式接收用户和公司参数，不把全部业务代码改成隐式 ThreadLocal 读取。
- 迁移期保留 `currentUserId/currentUsername` request attribute，避免 Controller 和测试一次性失效。
- 异步 Agent 任务必须显式捕获、传递和清理执行身份；不能依赖线程池继承请求线程的 ThreadLocal。
- 追踪 ID 与业务身份分开建模：追踪 ID 用于日志关联，用户/公司用于授权和数据隔离。

**实施状态（2026-09-19）：代码、单元回归和本机数据库迁移均已完成。** `AuthInterceptor` 明确为 order 0，Agent 拦截器 order 10 并只覆盖 `/auth/agent/**`；每个 Agent 请求按主键加载一次真实用户。Java 模型、Mapper 参数和本机运行库均已统一为 `String/VARCHAR(64)`；未认证返回 401，用户不存在、禁用或无公司返回 403，解析异常返回不泄漏细节的 500；成功、拒绝和异常路径均清理上下文。默认模式已改为 enterprise/fail-closed，已删除公司 `1` 回退。120 条既有 Agent 数据已按数据所有者批准的映射迁移为 `COMPANY202604050001`，行数保持不变，未改动现有 HTTP 路径、request attribute 或公共响应字段。

**功能影响：高。** 错误修复可能改变 Agent 可见数据范围。必须覆盖多公司用户、无公司用户、非法公司、异步执行和上下文清理测试，并保留回滚开关。

### 3.2 Support/Helper 数量与超大共享基座

**核验状态：确认存在，但旧报告的治理方式不合适。**

后端确有 7 个超过 2000 行的主代码文件：

| 文件 | 行数 | 当前判断 |
| --- | ---: | --- |
| `AbstractExpenseWorkflowSupport.java` | 4605 | 高风险共享运行时；路由、共享档案投影及付款回退决策已提取，审批/付款执行编排仍在原类 |
| `AbstractExpenseDocumentSupport.java` | 3869 | 遗留共享底座，已有多轮 owner 提取 |
| `AbstractFinanceVoucherSupport.java` | 2665 | Finance 凭证共享底座 |
| `AbstractFixedAssetSupport.java` | 2265 | 固定资产共享底座 |
| `FinancePeriodTransferServiceImpl.java` | 2155 | 仍直接承载较多业务真相 |
| `AbstractSystemSettingsDomainSupport.java` | 2152 | 已有多个子 owner |
| `LedgerReportDomainSupport.java` | 2002 | 报表业务热点 |

但命名为 `Support` 不自动等于职责错误。仓库已经采用“冻结 façade/入口、提取 owner、保持兼容委派”的绞杀式治理；例如 `SystemSettingsView.vue` 已从旧记录中的 2648 行收口到当前 480 行。旧报告把已完成的治理结果重新列为 P0，说明它没有正确区分文件历史体量、当前 live truth 和已冻结底座。

**治理决策：**

- 延续现有长期治理工作流：依据变更频率、跨域依赖、线上暴露面、测试缺口和 live truth 密度重排，不按行数机械排序。
- 现有超大基座冻结新增业务入口；新能力进入专属 owner，再由旧入口兼容委派。
- 每轮只治理一个主热点，完成 focused tests、全量测试和文档同步后再重排。
- 不进行“统一改成完整 DDD Entity/Repository/Event”的全量重写。
- 行数只作为告警信号；已冻结且低变更的底座可以暂时大于阈值。

**功能影响：中。** 分步提取要求对外接口、事务边界、状态机和序列化格式保持不变；整类重写则为高风险，明确禁止。

### 3.3 JSON 处理

**核验状态：轻度存在。**

P1 前报告只数到模型适配器中的 2 处手工实例；复核又发现 `DesensitizationMappingEntity` 中 2 处同类创建。当前树 100 个后端文件使用 `ObjectMapper`，生产代码手工 `new ObjectMapper()` 已降为 0。大量 JSON 调用来源于动态表单、流程配置和 Agent 配置，本身不等于重复造轮子。Spring 注入的 `ObjectMapper` 承担统一日期、模块和序列化配置。

**治理决策：**

- `LocalModelProvider` 和 `DeepSeekModelProviderAdapter` 已改为注入 Spring `ObjectMapper`；脱敏映射实体由仓储传入同一配置实例。
- 不创建静态 `JsonUtil`；静态工具会绕过 Spring Jackson 配置，并把领域错误压成不透明的通用异常。
- JSON 解析错误在各领域边界转换为可识别的业务错误；序列化底层异常保留 cause 和关联 ID。

**功能影响：低。** 需回归日期、金额、未知字段和 Agent 模型响应解析。

**P1 验证：** 脱敏映射 JSON 往返测试及后端全量测试通过；外部模型服务的真实响应未在本轮联网回放，上线前仍需环境冒烟。

### 3.4 验证逻辑

**核验状态：旧报告证据不足。**

当前至少 113 个 Java 文件使用 Jakarta Validation 或相关注解。业务代码中存在大量 `validate*`/`check*` 调用，但流程图校验、凭证平衡、期间状态、报销金额和权限判断是不同业务不变量，不能仅因方法名相似就合并。

**治理决策：**

- DTO 使用 Bean Validation 完成必填、长度、格式、范围等结构校验。
- 领域 owner 负责依赖数据库状态、权限、流程状态或跨字段关系的业务校验。
- 跨入口完全相同的规则才提取为具名 `*Policy`、`*Validator` 或 `*Rule`。
- 不创建一个跨 Expense、Finance、Process 的万能 Validator。

**功能影响：中。** 校验迁移可能改变错误顺序和提示语，必须锁定现有错误码、中文消息及边界条件。

### 3.5 配置类

**核验状态：不构成问题。**

按类名统计当前约 8 个 `*Config` 类。Agent、MVC、异步执行器、Jackson 等能力拥有局部配置是模块化的正常表现。集中成一个大配置类反而会扩大耦合。

**治理决策：**

- 保持模块内 `@ConfigurationProperties` 和配置类。
- 治理重复配置键、危险默认值、无法启动前发现的缺失配置，以及文档与实际环境变量不一致。
- 生产关键凭据必须启动失败而不是静默回退；本地开发回退必须明确且不能进入生产。

### 3.6 Agent 平台边界

**核验状态：部分存在。**

Agent 在同一 Spring Boot/MyBatis/Jackson/JWT 技术栈和同一数据库中运行，并非完全独立产品。其模型路由、对话、工具、编排和脱敏是智能层特有能力，不属于对主系统业务逻辑的重复实现。

P1 实施前确认的问题：

- 身份/公司上下文未正确接入，见 3.1。
- P1 前 `ExpenseDocumentControlledQueryTool` 和 `ExpenseQueryTool` 直接依赖 Process/Expense Mapper 与 Entity，违反“Agent 通过受控业务接口访问数据”的目标边界。
- Agent 自身 Mapper 依赖属于域内实现，可以保留；问题是跨域直接访问业务 Mapper。
- 脱敏能力只在 Agent 模型链路使用，主系统没有一套等价的通用脱敏系统，因此旧报告所称“两套脱敏规则”缺乏证据。

**治理决策：**

- Agent 继续作为“相对独立的智能增强层”，保留模型、工作流、工具和脱敏。
- 新增权限感知的 Expense 查询端口，端口内部负责所有权、待办范围、软删除、公司和权限判断，返回受限读模型。
- Agent Tool 只负责参数解析、调用端口和模型友好格式转换，不依赖业务 Mapper/Entity。
- 迁移前用 characterization tests 固定“我提交的单据”“待我审批的单据”、状态、日期、金额、关键字和条数限制行为。

**实施状态（2026-09-27）：P0 隔离和 P1 报销查询端口均已实施。** 两个报销 Tool 改用 `ExpenseAgentQueryPort` 的受限 DTO，不再依赖业务 Mapper/Entity。端口分别约束“我提交”与“待我处理”范围、单据提交人公司、软删除、筛选和最大 50 条；Agent Tool 在调用端口前校验请求身份与线程上下文一致，不让 Expense 反向依赖 Agent。P0 的 tenant/company/session 查询隔离、120 条本机数据迁移和单次发送会话读取 3→1 次保持不变。端口级测试通过；生产 Agent 模型调用及真实权限组合仍需上线前冒烟。

**功能影响：高。** 端口迁移会触及 Agent 查询结果范围，必须把“可见性不扩大”作为硬验收条件。

### 3.7 Process 与 Agent Workflow

**核验状态：不建议合并。**

Process 工作流负责审批模板、审批人、抄送、付款、分支和业务状态迁移；Agent Workflow 负责 LLM、工具、条件节点和运行步骤。二者都使用“节点/连线”并不意味着它们是同一种引擎。

**治理决策：**

- 不合并持久化模型、运行时、设计器和状态机。
- 可以复用无业务语义的图能力，例如节点键唯一性、连线完整性、拓扑排序和画布交互基础组件，但必须保持各自节点协议。
- 不让 Process 直接执行 Agent 工具，也不让 Agent 绕过 Process 修改审批状态；跨域动作通过明确命令端口完成。

**功能影响：高。** 工作流合并被列为“本阶段禁止项”。

### 3.8 Expense 与 Finance

**核验状态：部分存在。**

当前报销凭证推送通过 `FinanceVoucherService.saveVoucher()` 同步创建凭证，这已经是合理的命令边界；调用方需要立即得到凭证号、成功/失败结果，改成异步事件会改变用户操作语义。

确认的问题：

- Expense Voucher 代码直接使用 `GlAccvouchMapper` 查询科目编码，形成跨域数据访问。
- `pushDocuments()` 对外表达部分成功，外层事务中逐条捕获异常；而内部 `FinanceVoucherService.saveVoucher()` 也使用事务。必须用集成测试验证内部运行时异常是否把外层事务标记为 rollback-only，导致最终结果与“PARTIAL”语义不一致。

**治理决策：**

- 保留同步凭证命令；现有 `FinanceVoucherService` 可先作为命令端口，不为了命名再造一层空接口。
- 增加 Finance 参考数据查询端口，替换 Expense 对 `GlAccvouchMapper` 的直接访问。
- 明确批量推送是“每张单据独立提交、允许部分成功”。实现时每张单据使用独立事务边界，批次汇总在可预测的事务中更新。
- 增加数据库集成测试验证成功、业务校验失败、数据库异常、重复推送和批次部分成功。
- 领域事件仅用于凭证创建成功后的通知、审计或统计，不承担核心凭证创建。

**功能影响：高。** 事务调整可能影响凭证、推送记录和批次统计的一致性，必须支持按批次回查和安全重试。

**实施状态（2026-09-27）：** Expense 的科目选项读取已改经 `FinanceReferenceQueryPort`，由 Finance 实现原有的跨公司去重编码查询；单一元数据接口供多公司切换使用，不能仅按默认公司过滤而丢失既有选项。保留原有种子选项和同步 `FinanceVoucherService.saveVoucher()` 命令。批量入口移除外层整体事务，单据凭证与推送记录通过 `REQUIRES_NEW` 在同一事务提交；失败记录和批次汇总分别独立提交。已成功推送的单据拒绝再次创建凭证，失败重试不会擦除旧成功凭证号；批次号增加随机后缀，避免同秒重试碰撞唯一键。领域测试覆盖部分成功计数和重复推送，H2 隔离库验证数据库错误、回滚与重试；真实 MySQL 全链路回归仍是部署前门禁。

### 3.9 前端 API 层

**核验状态：当前方案合理。**

`src/api/modules` 采用能力模块与类型文件配对，`src/api/index.ts` 提供稳定兼容出口，并有 compatibility tests。模块拆分粒度不完全相同，是由领域复杂度和页面用例决定，不构成“各自为政”。当前最大 API 文件约 495 行，合并成“一领域一个文件”会重新制造大文件。

**治理决策：**

- 保留 `core.ts`、能力模块、`*-types.ts` 和 `@/api` barrel。
- 新增接口优先放入拥有业务语义的能力模块；只有出现循环依赖或重复模型时再提取共享类型。
- 保持现有导出名、请求路径和响应类型兼容。

### 3.10 异常处理

**核验状态：部分存在。**

项目已有 `GlobalExceptionHandler`，并非缺少统一入口。当前主要问题是业务代码广泛使用 `IllegalArgumentException`/`IllegalStateException`，错误码和可见消息依赖路径判断或文案，契约不够稳定。

**治理决策：**

- 先定义稳定错误响应字段和错误码，不立即批量替换所有异常类。
- 新增业务能力使用具名错误码；遗留异常通过全局处理器兼容映射。
- 禁止把内部 SQL、模型响应、密钥或堆栈直接返回前端。

### 3.11 缓存

**核验状态：条件触发后治理。**

系统并非“0 缓存”：Agent 脱敏映射存在 `ConcurrentHashMap` 缓存和数据库回源。目标并发约 50 QPS，尚无查询耗时、数据库负载或多实例一致性证据支持 Redis P0。

**治理决策：**

- 先测量慢查询、命中候选、数据更新频率和一致性要求。
- 单实例场景优先使用有界、带 TTL 和指标的本地缓存；敏感映射必须评估内存暴露和清理策略。
- 只有多实例共享、一致性、容量或性能数据证明需要时引入 Redis。
- 权限、配置和业务状态缓存必须定义失效机制后才能上线。

### 3.12 事件总线与消息队列

**核验状态：条件触发后治理。**

模块化单体中的直接 Service 调用可以提供清晰事务语义。为了解耦而统一改成 RabbitMQ/Kafka，会引入最终一致性、幂等、补偿、运维和故障排查成本。

**治理决策：**

- 核心用户操作保持同步命令。
- 同进程、提交后副作用可使用 Spring 事务事件，但监听失败不得破坏已提交核心业务。
- 需要跨进程可靠投递时必须同时设计 outbox、幂等键、重试、死信和监控，再决定消息中间件。

### 3.13 可观测性

### 4.1 版本库中的令牌文件

**核验状态：确认存在，当前树已处置。** `tmp-admin-token.txt` 已从工作树和 Git 索引移除，报告不记录令牌内容；Git 历史未清洗。

4. 评估历史中是否还有可用凭据；只有在团队协调、备份和全员重新同步方案完成后，才清洗 Git 历史。

凭据应具备创建、轮换、撤销、过期和泄漏处置生命周期，参考 [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)。

**实施状态（2026-09-18）：** 已增加精确 `.gitignore` 规则、本地 JWT 随机轮换脚本、当前树 secret 扫描和 GitHub 质量门禁；本机忽略文件中的 JWT 签名密钥已随机轮换且未回显。本机 8081 端口当时没有运行服务，因此没有伪造“已完成旧 JWT 401/新登录成功”的运行态证据。生产凭据未被本轮直接修改。

**功能影响：高。** 轮换可能使现有脚本、浏览器会话和自动任务失效；必须先盘点使用方。Git 历史清洗影响所有协作者，本轮禁止自动执行。

### 4.2 无盐 MD5 密码

**核验状态：确认存在，兼容迁移已实施。** 治理前登录、个人中心改密及财务敏感操作使用 `DigestUtil.md5Hex()` 比对密码。

**处置决策：**

- 引入 Spring `PasswordEncoder` 抽象，目标编码采用 bcrypt，cost 12。
- 新密码只写入 bcrypt。
- 登录时识别遗留 32 位 MD5；MD5 验证成功后在同一用户范围内立即重哈希为 bcrypt。
- 长期未登录用户由管理员触发密码重置；迁移完成后移除 MD5 分支。
- 财务敏感操作复用同一个 PasswordEncoder，不保留第二套校验。

OWASP 要求密码使用带盐、自适应的现代哈希算法，不应使用 MD5 等快速哈希；详见 [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

**功能影响：高。** 必须覆盖登录成功/失败、并发升级、改密、旧密码确认和回滚；不得一次性使全部用户失效。

**实施状态（2026-09-18）：** 新增内部 `PasswordHashService` 和显式 `spring-security-crypto` 依赖。bcrypt cost 固定为 12；60 字符 `$2a$/$2b$/$2y$` 走 bcrypt，32 位十六进制值走遗留 MD5 常量时间比较，未知或损坏格式统一失败。登录、改密、反结账/反记账、手工员工创建和组织同步入口已统一使用该组件。遗留 MD5 登录成功后以 `id + 原哈希` 条件更新，竞争时只重读一次确认；新密码和默认密码不再写 MD5。数据库列 `VARCHAR(64)` 无需改表，也未执行离线批量重哈希。

### 4.3 红灯基线

**核验状态：原基线确认存在，当前已恢复绿色。** 后端全量测试、前端单测和前端类型检查的原始红灯均已按原因修复。

**处置决策：**

- 先按“测试基础设施/夹具漂移、真实业务回归、环境隔离”三类归因。
- 修复类型检查和真实业务回归；更新因构造器、前置条件变化而失效的测试夹具。
- 补齐 Element Plus 共享 Mock 后重新计算前端真实失败数。
- 恢复全绿之前，不启动跨域大重构、工作流合并或密码以外的高风险迁移。

**实施状态（2026-09-18）：已验证。** 后端 749/749、前端 655/655、类型检查和生产构建均通过。没有删除断言、跳过测试、关闭类型检查或放宽生产校验；修复内容包括环境变量隔离、银行账户 `accountId` 夹具、模块启用夹具、付款完成状态、越界年份事件、按钮定位以及 Element Plus Mock。

### 4.4 生产 JWT 轮换操作手册

生产环境只能由有权限的运维人员在变更窗口执行，且不得把新密钥写入工单、聊天或终端历史：

1. 盘点依赖旧 JWT 的浏览器会话、脚本、定时任务和集成方，提前声明全量登录失效窗口。
2. 在受控终端生成新的 32 字节随机 Base64URL 值，写入同目录临时文件中的 `FINEX_JWT_SECRET`，不输出值。
3. 将临时文件权限限制为服务账号可读，并以原子 rename 替换 `/opt/finex/backend/.env.production`；禁止先删除正式文件后再写入。
4. 重启 Auth Service，确认配置加载成功、健康检查正常，旧 JWT 对受保护接口返回 401。
5. 使用新登录签发的 JWT 验证一个只读接口和一个权限受控接口；失败时生成另一枚新密钥或回滚应用构建，但不得恢复已泄漏旧密钥。
6. 撤销旧凭据的所有副本并记录轮换时间、执行人、验证结果和下一次到期时间。Git 历史清洗继续作为独立高风险变更。

### 暂不治理或条件治理

- 合并 Process 与 Agent Workflow。
- 全量重写所有 Support（禁止的是“大爆炸重写”；超大文件本身已列为 P3 持续治理）。
- 把前端 API 合并成一个领域巨型文件。
- 新建全局静态 `JsonUtil` 或万能 Validator。

- 无可靠异步需求引入 RabbitMQ/Kafka。
- 当前阶段拆分微服务。

## 六、架构护栏决策

### 6.1 可自动执行的依赖规则

ArchUnit 用于字节码可验证的规则：

- Controller 不直接依赖 Mapper。
- Controller 原则上只依赖 Service/应用端口；遗留例外进入显式白名单。
- Agent Tool 不依赖 Expense/Process/Finance Mapper。
- 业务端口不依赖 Web Controller 或具体适配器。

当前包结构仍以技术分层为主，不能直接用 `com.finex.auth.(*)..` 宣称领域无环；应先建立真实领域包或显式模块清单，再启用无环规则。

### 6.2 文件体量规则

源文件行数不交给 ArchUnit；P3 已使用独立仓库脚本：

- 生产 Java 新文件超过 1000 行、生产 Vue/TypeScript 新文件超过 800 行由 `scripts/check-large-files.ps1` 阻止。
- 28 个既有超限文件已进入版本化基线；净增长失败，白名单只能缩小。测试文件尚未纳入该门禁。
- 体量告警必须与变更频率、复杂度和测试缺口结合评估。

### 6.3 质量门禁

- 后端：compile、focused tests、全量 `verify`（测试、ArchUnit、JaCoCo 53% 整体行覆盖率下限）。
- 前端：type-check、focused tests、全量 tests、production build。
- 架构：新增依赖规则无违规，遗留白名单不得增加。
- 体量：新生产文件不得超限，28 项遗留上限不得增长；每次 owner 提取必须保留行为回归。
- 文档：重大边界、接口、配置和部署变化同步更新。
- 覆盖率：P3 本次后端 JaCoCo 已测得 53.67%；70% 仍是目标，前端覆盖率工具尚未接入。

## 七、最终判断

系统确实存在架构债务，但不是旧报告所描述的“所有模块都重复造轮子”。更准确的判断是：

1. 系统仍是单一业务部署模块中的逻辑分域；P2 已对首批字节码边界加自动护栏，但尚无完整的领域包隔离。
2. P3 已把超大文件从“暂不治理”拆出：防增长门禁、后端/前端首刀、审批路由、共享档案条件与付款撤销/回退状态策略已落地；最大文件从 5196 行降至 4605 行，28 个遗留例外仍需持续收口，不能宣称清零。
3. Agent 的模型、工具、工作流和脱敏具有独立业务语义，应保留；认证、公司隔离和报销查询端口已分阶段治理。
4. Expense–Finance 保留同步凭证命令；科目查询端口与单据级事务已实施，真实 MySQL 凭证链路仍需发布前回归。
5. Redis、消息队列和统一工作流不是当前 P0。凭据、密码、身份隔离和绿色测试基线才是。

本报告后续复查必须重新执行指标和测试命令，不得复制本次数字作为永久事实。P0 的密码迁移、绿色门禁、当前树 secret/编码护栏、本机密钥轮换、Agent 止血和 120 条本机数据公司编码迁移，以及 P1 五项代码治理均已完成。P2 已落地首刀 owner 提取、覆盖率实测与门禁、精确依赖白名单、性能统计工具和漂移检查机制。P3 已建立超大文件防增长护栏并完成后端/前端首批职责提取；28 项遗留清单继续逐刀收口。付款本地事务边界仅经隔离测试验证，现有“银行推送/回单”仍是本地模拟，真实银行集成未完成且不得用于真实付款。尚未完成的外部事项包括生产 JWT 轮换及其运行态验证、真实 MySQL 凭证链路与 Agent 模型冒烟、银行沙箱联调、Git 历史清洗评估和广泛性能压测；这些不能凭单元测试结果冒称已验证。
