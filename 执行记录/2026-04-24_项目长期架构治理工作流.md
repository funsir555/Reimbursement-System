## 3. 长期目标架构

未来 12-18 个月的目标架构固定为：

> 模块化单体 + 自动化架构护栏 + 文档化决策 + 可批量治理工具链

这意味着：

- 继续以单体分域治理为主
- 为未来可拆分预埋清晰边界
- 不直接把当前路线改写成全面微服务化计划
- 不再让“架构治理”只依赖人工记忆和口头约定

## 4. 对标方法论与落地方式

### Spring Modulith

用途：作为模块化单体的目标范式，用于约束 `auth-service` 内部子域边界、模块依赖和事件协作方式，而不是立刻引入新的部署单元。

参考：<https://docs.spring.io/spring-modulith/reference/>

### ArchUnit

用途：把层级、包依赖、禁止反向依赖、禁止 controller 直连 mapper 等规则变成架构测试。

参考：<https://www.archunit.org/userguide/html/000_Index.html>

### OpenRewrite

用途：作为后续重复技术债批量治理工具，用于 import、包迁移、API 替换、注解替换、测试模板统一。

参考：<https://docs.openrewrite.org/>

### Testcontainers

用途：作为更稳定的后端集成测试基础设施，减少环境漂移带来的回归成本。

参考：<https://java.testcontainers.org/>

### ADR

用途：作为重大架构决策留痕机制。凡是新增 owner、调整边界、调整事务 / 事件策略、允许例外依赖，都应该有 ADR。

参考：<https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html>

### C4 Model

用途：作为长期文档呈现标准，统一上下文图、容器图、组件图，不再让 README、架构图、治理文档各说各话。

参考：<https://c4model.com/>

## 5. 明确不采用的路线

未来 12 个月内不作为主线：

- 不把 Backstage / 平台化门户作为首批目标
- 不把服务网格、全面微服务、事件总线平台化作为主实施路径
- 不优先重打已冻结 façade，除非复盘再次确认其重新膨胀
- 不为了“先进”而脱离当前仓库的真实落地节奏

## 6. 长期治理循环

每一轮治理都按固定 8 步执行：

1. 月度 hotspot 扫描：按体量、变更频率、跨域依赖、测试缺口、文档漂移、线上暴露面打分
2. 批次选题：每轮只选 1 个主热点 + 0-1 个陪跑热点，禁止并发失控
3. 边界建模：定义 owner、冻结入口、允许依赖、禁止依赖、live truth 落点
4. 设计留痕：写 ADR，必要时更新 C4 / 领域边界图，并明确“不做什么”
5. 渐进收口：按“抽边界 -> 迁移调用 -> 冻结旧入口 -> 补护栏”推进
6. 自动化护栏：补 ArchUnit、focused tests、controller compatibility tests、启动脚本与配置校验
7. 文档对齐：回写治理基线、领域边界、README、启动说明
8. 复盘与重排：重新跑统一评分模型，决定下一批，而不是凭感觉换目标

## 7. 评分模型

每个候选热点至少按以下维度统一评分：

- 体量分
- live truth 集中度
- 变更频率
- 跨域耦合度
- 测试缺口
- 文档 / 配置漂移度
- 线上风险暴露面

## 8. backlog 分层

### `L1`：live business hotspot

定义：仍直接承载 live truth，继续膨胀会立刻放大业务风险的热点。

说明：原 second-wave 四个热点已经全部完成，本层下一批需要重新 re-rank 决定，不再沿用旧固定顺位。

### `L2`：owner base / shared support 膨胀点

定义：不再是第一入口，但正在长成新的大基座，未来可能形成第二轮屎山。

当前重点观察对象：

- `AbstractExpenseDocumentSupport`
- `AbstractExpenseWorkflowSupport`
- `AbstractProcessManagementSupport`
- `AbstractFixedAssetSupport`

### `L3`：文档、配置、脚本、运行链治理项

定义：不直接承载业务真相，但会持续拉低项目可维护性。

典型对象：

- README 与架构文档乱码
- 配置口径漂移
- 启动链不稳定
- tracked `.m2`
- 测试构造器漂移
- 重复运行脚本

## 9. 分轨治理策略

### 9.1 后端轨道

- 按子域 owner 持续收口
- 引入模块边界测试和依赖白名单
- 持续约束 frozen facade 不回灌 live truth
- 把启动链、配置契约、环境变量、脚本一致性纳入治理

### 9.2 前端轨道

- 不再只做 API barrel 兼容
- 每轮后端热点治理必须同步检查对应前端 view / editor / api module / store 是否形成二次热点
- 控制 `View.vue -> Panel / Editor / Drawer -> api / store / schema` 的层级与体量

### 9.3 文档与配置轨道

- 统一 UTF-8
- 统一事实口径
- 统一主文档引用关系
- 统一启动说明与实际行为
- 发现乱码时，默认进入优先修复，而不是继续带病积累

## 10. 节奏、验收与指标

### 10.1 固定节奏

- 每周：轻量 hotspot 扫描
- 每两周或每月：选一个治理批次
- 每季度：做一次 residual re-rank 与文档基线审计

### 10.2 固定验收口径

- 结构验收：边界、依赖、包归属、冻结入口是否符合规则
- 测试验收：compile、focused tests、full test、必要时前端单测
- 运行验收：启动链、本地脚本、关键 smoke path
- 文档验收：治理文档、领域边界、启动说明、README 是否同步

### 10.3 固定长期指标

- 单文件行数上限与超限清单
- frozen facade 数量与回流次数
- 每轮治理净减少的热点数
- 测试通过率
- 文档同步率
- 配置漂移 / 启动故障次数

## 11. 退出条件

本工作流的目标不是把项目变成“没有大文件”的项目，而是把热点从“live truth mega file”降级成：

- 可控 owner
- 可测基座
- 可审计边界
- 可持续复盘的工程结构

只要这个循环还能持续压制新屎山，治理就是有效的。
